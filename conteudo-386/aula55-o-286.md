## O problema que o 286 resolveu

No 8086, um segmento é só um número que se multiplica por 16. Qualquer programa escreve em qualquer lugar: na tabela de interrupções, no DOS, no código de outro programa. Para um sistema de um usuário e um programa por vez, como o DOS, isso nunca foi grave. Para um sistema com vários programas ao mesmo tempo, como o Unix que rodava em minicomputadores, é inaceitável: um programa com defeito derruba todos.

Em 1982 a Intel lançou o **80286**, e com ele o **modo protegido**. A ideia: o valor num registrador de segmento deixa de ser um endereço e passa a ser um **seletor**, um número que escolhe uma linha numa tabela mantida pelo sistema operacional. Cada linha, um **descritor**, diz onde o segmento começa, qual o tamanho dele e o que se pode fazer com ele. A CPU confere tudo isso a cada acesso. Se um programa passar do fim do segmento, escrever num segmento de código ou usar um seletor que não é dele, a CPU interrompe com uma **exceção** em vez de deixar o estrago acontecer.

O 286 também tinha 24 fios de endereço: **16 MB** de memória, contra 1 MB do 8086. Mas no modo real ele continuava sendo um 8086 rápido, preso no primeiro megabyte. O IBM PC AT (1984) usava o 286, e quase todo mundo usou o AT como um PC XT mais rápido, com DOS e no modo real.

## Do segmento ao seletor

No modo protegido, um registrador de segmento guarda um seletor de 16 bits dividido em três partes:

```diagrama titulo="Um seletor"
 15                              3   2   1  0
+----------------------------------+---+------+
|      índice (0 a 8191)           | TI | RPL  |
+----------------------------------+---+------+
  índice: qual descritor da tabela
  TI:     0 = GDT (tabela global), 1 = LDT (tabela local)
  RPL:    nível de privilégio pedido (0 a 3, módulo 22)
```

Como o índice começa no bit 3, o seletor de um descritor da GDT com RPL 0 é **índice × 8**: o descritor 1 é o seletor 08h, o 2 é o 10h, o 3 é o 18h. Cada descritor ocupa exatamente 8 bytes, então o seletor (sem os 3 bits de baixo) já é o deslocamento do descritor dentro da tabela. Não é coincidência: a Intel desenhou assim para a CPU achar o descritor sem multiplicar.

O descritor 0 da GDT é o **descritor nulo**. Ninguém usa: o seletor 0 serve para dizer "este registrador não aponta para nada".

## O descritor do 286

```diagrama titulo="Descritor de segmento do 286 (8 bytes)"
byte 0-1   limite (16 bits): o último deslocamento válido
byte 2-4   base (24 bits): onde o segmento começa na memória
byte 5     acesso:
             bit 7    P     presente (1 = está na memória)
             bits 6-5 DPL   privilégio do segmento (0 a 3)
             bit 4    S     1 = código ou dados, 0 = sistema
             bits 3-0 tipo  para S = 1:
                              1010 (Ah) código, pode ler
                              1000 (8h) código, só executar
                              0010 (2h) dados, pode escrever
                              0000 (0h) dados, só ler
                              bit 0 = A: a CPU põe 1 quando usa o segmento
byte 6-7   reservado no 286, tem que ser 0 (o 386 usa)
```

Os acessos mais comuns, prontos:

| Byte de acesso | Significado |
|---|---|
| `9Ah` | presente, DPL 0, código com leitura |
| `92h` | presente, DPL 0, dados com escrita |
| `FAh` / `F2h` | o mesmo com DPL 3 (para programas de usuário) |

Em NASM, um descritor do 286 se escreve campo por campo:

```nasm fragmento titulo="A tela de texto como um segmento"
video:  dw 0FFFh                ; limite: 4 KB (80 x 25 x 2 = 4000 bytes)
        dw 8000h                ; base, bits 0-15
        db 0Bh                  ; base, bits 16-23: base = 0B8000h
        db 92h                  ; presente, DPL 0, dados com escrita
        dw 0                    ; reservado
```

Com esse descritor em ES, `mov [es:0], ax` escreve no canto da tela, e `mov [es:1000h], ax` causa uma exceção: o deslocamento 1000h passa do limite 0FFFh.

:::cpu Os registradores escondidos
Ler o descritor na memória a cada acesso seria lento demais. Quando um seletor é carregado num registrador de segmento (`mov ds, ax`), a CPU lê o descritor uma vez e guarda base, limite e acesso numa parte escondida do registrador, o **cache do descritor**. Os acessos seguintes usam a cópia. Consequência importante: mudar o descritor na memória não muda nada até o seletor ser carregado de novo. O 8086 do modo real também tem esses caches; nele, a base é sempre o segmento × 16 e o limite é FFFFh. Guarde isso para o "unreal mode" do módulo 19.
:::

## A GDT e o LGDT

A **GDT** (tabela global de descritores) é um vetor de descritores em qualquer lugar da memória. A CPU sabe onde ela está pelo registrador **GDTR**, carregado com `lgdt [m]`, onde `m` aponta para 6 bytes:

```nasm fragmento titulo="O operando do LGDT"
gdtr:   dw fim_gdt - gdt - 1    ; limite: tamanho da tabela menos 1
        dd gdt                  ; base: endereço linear da tabela (o 286 usa só 24 bits)
```

O endereço é **linear**, não segmento:deslocamento. Num setor de boot com `org 7C00h` e DS = 0, o endereço do rótulo já é o linear. Num .COM, seria preciso somar o segmento × 16.

## A MSW e o LMSW

O 286 tem uma **palavra de estado da máquina** (MSW) de 16 bits. O bit 0, **PE** (*protection enable*), liga o modo protegido. Duas instruções mexem nela: `smsw` lê e `lmsw` escreve. No 386, a MSW virou a metade de baixo do registrador **CR0**, e as duas instruções continuam existindo por compatibilidade.

Ligar o PE não basta. Logo depois, CS ainda tem o valor do modo real, e a CPU já buscou as próximas instruções da memória do jeito antigo (a fila de pré-busca). Um **salto far** resolve as duas coisas de uma vez: esvazia a fila e carrega CS com um seletor de verdade.

```nasm executar modo="boot" titulo="PM286.BIN: entra no modo protegido como no 286"
        bits 16
        org 7C00h
        cli                     ; nada de interrupções: a IVT não vale mais no modo protegido
        xor ax, ax
        mov ds, ax
        lgdt [gdtr]
        smsw ax
        or ax, 1                ; PE = 1
        lmsw ax
        jmp 08h:protegido       ; salto far: CS = seletor 08h (descritor 1)

protegido:
        mov ax, 10h             ; dados: base 0, 64 KB
        mov ds, ax
        mov ss, ax
        mov sp, 7C00h
        mov ax, 18h             ; a tela
        mov es, ax
        mov si, msg
        xor di, di
        mov ah, 1Eh             ; amarelo no fundo azul
.laco:  lodsb
        test al, al
        jz .fim
        stosw
        jmp .laco
.fim:   cli
        hlt

msg:    db 'Modo protegido de 16 bits, como no 286!', 0

gdt:    dq 0                    ; 00h: o descritor nulo
        dw 0FFFFh, 0            ; 08h: código, base 0, limite FFFFh
        db 0, 9Ah
        dw 0
        dw 0FFFFh, 0            ; 10h: dados, base 0, limite FFFFh
        db 0, 92h
        dw 0
        dw 0FFFh, 8000h         ; 18h: a tela, base 0B8000h
        db 0Bh, 92h
        dw 0
fim_gdt:
gdtr:   dw fim_gdt - gdt - 1
        dd gdt

        times 510 - ($ - $$) db 0
        dw 0AA55h
```

Rode passo a passo e acompanhe o painel: depois do LMSW o MODO muda para "modo protegido 16 bits", CS ainda vale 0000h, e só depois do salto far CS vale 0008h. A lista de eventos explica cada passo, e o quadro da GDT mostra os quatro descritores.

:::atencao Nada de BIOS no modo protegido
As rotinas da BIOS foram escritas para o modo real: usam segmentos como números e a tabela de interrupções em 0000:0000. No modo protegido, um `int 10h` procura a interrupção 10h numa outra tabela (a IDT, módulo 20), que este programa nem criou. Por isso ele escreve direto na memória da tela, e por isso começa com `cli`: um tique do relógio também viraria uma interrupção sem tratador.
:::

```quiz

> O índice começa no bit 3: 5 × 8 = 40 = 28h. TI = 0 (GDT) e RPL = 0 completam os bits de baixo.
```

## E para voltar ao modo real?

No 286, não dá: o LMSW liga o PE, mas não desliga. A Intel imaginou que um sistema que entrou no modo protegido nunca mais ia querer sair. Só que o DOS e a BIOS só funcionavam no modo real, e programas como o RAMDRIVE e o HIMEM queriam usar a memória acima de 1 MB e voltar.

A solução da IBM foi **resetar a CPU sem resetar o PC**:

1. o programa escreve um código na posição **0Fh da CMOS** (o *shutdown status byte*) e guarda um endereço de volta em 0040:0067;
2. manda o controlador do teclado puxar o fio de reset da CPU (comando **FEh** na porta 64h);
3. a CPU reinicia no modo real e executa a BIOS, que lê a CMOS, vê o código e, em vez de dar boot, salta para o endereço guardado.

Levava milissegundos. Mais tarde se descobriu um jeito mais rápido: provocar de propósito uma **falha tripla** (uma exceção sem tratador durante o tratamento de outra), que também reseta a CPU. O OS/2 1.x fazia isso. O 386 acabou com o problema: nele, basta zerar o bit PE do CR0 com `mov cr0, eax`, e você vai fazer isso no módulo 19.

:::anos90 "O 286 é um cérebro morto"
Bill Gates chamou o 286 de *brain-damaged* por causa disso: o OS/2 1.x precisava voltar ao modo real para rodar programas do DOS, e cada volta era um reset. O Windows 3.0 rodava no "modo padrão" no 286 e no "modo 386 aprimorado" no 386, que usava o modo virtual 8086 do módulo 24 em vez de resets.
:::

## A diretiva cpu 286

Para garantir que um programa só usa o que o 286 tem, comece com `cpu 286`. Aí `lgdt`, `lmsw` e `smsw` valem, mas registradores de 32 bits e `mov cr0, eax` são recusados com uma explicação. O exercício 2 pede exatamente isso.

:::resumo
- No modo protegido, um registrador de segmento guarda um **seletor**: índice, tabela (GDT ou LDT) e RPL. Seletor da GDT com RPL 0 = índice × 8.
- O **descritor** de 8 bytes diz base, limite e acesso. No 286 a base tem 24 bits (16 MB). 9Ah = código, 92h = dados.
- `lgdt` carrega o endereço linear e o limite da GDT; `lmsw` liga o PE; um salto far carrega CS e esvazia a fila.
- A CPU guarda o descritor num cache escondido quando o seletor é carregado.
- O 286 não volta ao modo real sem um reset da CPU (CMOS 0Fh + comando FEh, ou falha tripla). O 386 volta zerando o PE.
:::
